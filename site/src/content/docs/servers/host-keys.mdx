When a server sends a different host key than the one in your `known_hosts` (it was
reinstalled, its keys were rotated, or someone is in between), desk refuses to connect, as ssh
does. The pane's connection box shows what matters.

![db-02's pane, and over it the box "db-02's host key changed"](../../../assets/shots/srv-hostkey.png)

## The box

<figure class="cut">

![db-02's host key changed. sent now ED25519 SHA256:…; known ED25519 SHA256:… in ~/.ssh/known_hosts:3. Close pane C, Accept new key A, Reconnect R](../../../assets/shots/srv-hostkey-box.png)

<figcaption>The key the server sent now, and the one you have, side by side.</figcaption>
</figure>

- **sent now**: the type and SHA256 fingerprint of the key the server sent.
- **known**: the key you have for it, from your `known_hosts` (or what `KnownHostsCommand`
  printed), and **in** which file and line. One pair for each line with another key for that
  host or its `HostKeyAlias`.
- Under them: "It sent another key than the one you have for it. If it was reinstalled or its
  keys rotated, accept the new one: desk drops the old line from known_hosts, saves the key it
  sent and connects. Not expecting a change? Don't: someone may be in between."

Compare the fingerprint with the one the server's owner gives you (on the server,
`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`) before you accept.

| Button | Key | What it does |
|---|---|---|
| **Close pane** | <kbd>C</kbd> or <kbd>Esc</kbd> | Closes the pane. Nothing changes. |
| **Accept new key** | <kbd>A</kbd> | Replaces the old line with the key shown, and connects. |
| **Reconnect** | <kbd>R</kbd> | Tries again as it is, for example after you fixed `known_hosts` yourself. |

**Accept new key** only shows when a `known_hosts` line holds the old key.

## What Accept new key does

<Steps>

1. desk checks each of those lines: it must still hold the old key, for that host. Hosts
   written as names, `[host]:port` or hashed (`|1|…`) all count.

2. It deletes those lines, and only those. Every other line stays, and the file keeps its
   permissions.

3. It adds the key the server sent, the one in the box, to your first `UserKnownHostsFile`
   (hashed when `HashKnownHosts` says so), and reconnects.

</Steps>

![db-02 connected again, at its prompt](../../../assets/shots/srv-hostkey-accepted.png)

It's what `ssh-keygen -R` and a reconnect would do by hand, except that the key saved is the one
you saw: a server that sends yet another key on the reconnect is refused again.

## What it doesn't do

- **It doesn't check that the new key is genuine.** Check the fingerprint first.
- If any line no longer holds that key for that host (you edited the file meanwhile), desk drops
  nothing at all and says so: "… no longer holds that key; nothing dropped".
- A key that came from `KnownHostsCommand` can't be dropped: change what the command prints.
- It doesn't touch other hosts' lines, or other keys of this host.

If it fails, a toast says why, starting with "accepting the new host key:".
